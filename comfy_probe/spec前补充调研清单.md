# spec 前补充调研清单

日期：2026-10-11。承接《本机调研与工作流接入建议》，本轮只读检查本机源码和现有任务查询接口，没有运行新生成任务、重启服务或修改 ComfyUI。

## 已有依据与本轮新增发现

正常调用已有依据：五次成功生成、图片上传、WebSocket 采样进度、输出与临时预览回收、实际种子、MP4 音视频解码、一个等待任务的定向取消。当前 `/api/jobs/{job_id}` 查询成功返回此前视频的 completed 状态；实时队列为空。

本轮确认的接口与约束：

| 事项 | 本机依据 | 对设计的影响 |
| --- | --- | --- |
| 任务 ID | server.py:1090 起允许客户端提供合法 UUID | 应用先持久化自己的执行 ID/请求，再提交，可用于响应丢失后的核实 |
| 提交去重 | server.py:1131 调用入队；execution.py:1262 起直接 heapq.heappush，没有按 ID 去重 | 相同 ID 不能当作服务端幂等保证；超时后不可盲目重新提交 |
| 队列/history | execution.py:1251 起在对象内创建列表和字典 | ComfyUI 重启后这些记录不能作为恢复依据；应用必须自己持久化 |
| history 保留 | execution.py:1249 上限 10000，1286 起完成时写入并淘汰旧记录 | history 不适合作为长期创作档案；任务不存在不等于没有执行过 |
| 成功与 history 的时序 | execution.py:824 发送 execution_success；main.py:377 起随后 task_done 写入 history | 收到成功事件后 history 可能暂未可读，需短暂核实/重试读取，不应重做生成 |
| WebSocket 重连 | server.py:289 起仅补发当前节点；同 clientId 会替换旧 socket | 重连不能假定补齐所有历史事件；每个应用连接应有明确身份并结合查询恢复 |
| 定向取消 | server.py:944 起；execution.py:1323 起在队列互斥锁内检查并中断指定任务 | 当前版本优先使用 POST /api/jobs/{job_id}/cancel，避免取消落到下一项任务 |
| 取消返回值 | server.py:975 起已结束/未知任务返回 cancelled=false | 返回值与实际终态分别处理；“已请求取消”不等于“已取消完成” |
| 旧 interrupt | server.py:1160 起先查状态后发全局中断标志 | 即使携带 ID，旧路径也缺少新接口的原子性；兼容旧版本需单独设计 |
| 部分产物 | execution.py:826 起收集已输出的 UI 结果进入 history_result | 保存不应仅发生于成功终态；失败/取消的可读取产物也应收集，仍待异常实测 |

以上是当前安装版本的源码检查结论，未通过重启、网络丢包或运行中中断来验证所有异常行为。源码文件位于 `F:\ComfyUI\ComfyUI_windows_portable\ComfyUI`。

## 写 spec 前应明确的六个问题

### 1. 执行协议和恢复边界

需要定义本地任务 ID、ComfyUI prompt_id、连接 client_id 的对应关系；提交前保存请求；收到确认、提交结果未知、等待、执行、取消请求、保存、完成、失败、取消和结果缺失的状态转换。

尤其覆盖：提交请求成功但响应丢失；WS 断线但任务继续；成功事件早于 history 可见；应用退出后 ComfyUI 继续运行；ComfyUI 重启；生成完成后复制失败；一部分产物已保存；重复点击执行。

spec 可据现有源码确定原则：不盲目重提交、不将断线伪装成失败、不将未知伪装成成功、生成与资产落盘是不同阶段。异常实测应在后续受控适配器测试中完成，避免为调研打断用户正在使用的服务。

### 2. 生产使用的工具契约

已有低负担测试尚不足以选定所有正式默认值。应针对正常尺寸编辑、Qwen 快/质量档、正常视频时长/分辨率、非正方形输入做少量代表性试验，记录时间、显存/内存和实际输出尺寸。

每个工具明确：必需/可选输入及数量、输入比例处理、参数类型与边界、固定模型/LoRA、预设配套关系、输出角色、可否批量、种子语义、失败分类与工具版本。

“调亮”“保持人物”“换背景”等反馈需要映射到已验证的编辑指令能力。没有独立明暗数值控件就不应在工具契约里虚构一个。明确提示词可表达的目标与能够硬性保证的输出属性。

### 3. 语言模型与 agent 的执行约束

尚未选择/连接语言模型。这是未调研的组件，应验证中文意图理解、结构化计划或工具调用输出、未知工具/参数处理、费用与超时信息是否可获得。

建议 agent 的边界：读取项目和明确素材信息 → 准备结构化计划 → 用户调整/执行 → 后台校验和执行 → 呈现结果与改动依据 → 等待反馈。文件复制、队列、参数校验、资源限制、版本记录交给确定性后台。

应准备代表性语句检验计划：“调亮但保留夜景”“用选中的这张”“放大两倍”“用上一张做视频”，以及“选中素材已被移除”“有多个候选却只说刚才那张”“请求工具没有的能力”“模型输出了不存在的素材 ID”。测试以计划准确性和处理边界为主，不必每条都消耗 GPU。

模型服务可设计为可替换。最终供应商/本地部署、费用预算与密钥配置取决于用户选择；无需为写产品需求先承诺某个品牌。

### 4. 上下文和素材引用规则

需要明确当前项目、明确选中项、候选批次、最佳标记、上一条完成任务、上一轮编辑输入各自的含义和引用优先级；不能仅靠“最后一个文件”。

计划准备完成后锁定输入 asset_id 和工具版本。用户改选素材、改参数或改变计划，应重新形成待执行版本，防止执行旧计划。多候选有歧义时询问，跨项目引用通过明确资产关系完成。

项目目标/风格、近期对话、实际执行参数与用户选择应形成可控的上下文快照；不默认增加看图评价或跨会话风格学习。

### 5. 素材身份、落盘与删除

需要研究并写清应用内资产、物理文件、项目引用、任务输入/输出、候选批次、版本派生关系的区别。

本次已证实 final 与 temp PNG 可以像素相同但文件 hash 不同。需要选择内容去重策略；至少避免把末端预览误当额外版本。角色与出处应独立于物理文件存储。

保存协议应支持临时文件、校验、原子完成和补存；数据库记录与文件复制之间的异常需要恢复。软移除不破坏 lineage；永久清理检查其他项目引用与来源记录，释放空间按实际文件统计。导入、复用、归档及删除应有各自的语义。

具体 SQLite/文件目录等实现方案可以由实现者选择；这些一致性与数据归属规则应进入 spec。

### 6. 资源约束与外部任务共存

本次已看到大模型运行时可用内存较低。需要确定初始尺寸/时长/批量档位、应用队列上限、任务超时、手动重试边界，以及是否/何时释放模型缓存。

用户仍可能通过 ComfyUI 原界面提交任务。应用不能只看自己的任务表，还要观察服务器队列，不抢占、取消或清理其他来源任务。助手对话创作忙碌时新诉求的处理，也需与手动工具排队规则区分。

本地生成没有按次云端积分，不代表没有资源消耗。语言模型费用应根据可获取的 token usage 与价格估算；价格/usage 缺失时显示未知或估算依据，避免精确金额表象。耗时、GPU 使用和费用分别限制。

## 建议的调研顺序

1. 先确定执行协议、状态机、资产归属与异常恢复原则；本轮接口检查已有足够依据。
2. 选定或确认可用的语言模型服务，做中文结构化计划与素材引用测试。
3. 为首批工具补少量正常配置试跑，形成初始预设和清晰能力范围。
4. 写 spec 时把运行中取消、丢包、重启、空间不足等未实测情形列成验收场景，随后在实现阶段做受控验证。

spec 应把已实测、源码确认、设计决定和待验证假设明确分开。调研做到影响架构与用户承诺的事实有依据即可；边界情况不能因尚未全部实测而消失在设计中。
