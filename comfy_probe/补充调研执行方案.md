# 补充调研执行方案

日期：2026-10-11。本文提出调研方法和建议设计，不是最终 spec，也不代表下面的验证已经全部执行。

## 建议采用的基本结构

浏览器工作台连接独立的本地应用后台。后台包含项目/素材存储、工具注册、任务调度、ComfyUI 适配器和语言模型适配器。应用使用自己的运行环境与数据目录，ComfyUI 继续由用户启动和维护。

建议使用 Python 后台与 SQLite 元数据存储，素材文件位于应用自己的素材目录。这里是实现建议，可在 spec 中最终决定。数据库事务与素材文件写入是两套操作，需要显式的保存/补偿协议，不能把外部文件复制当成已经受 SQLite 事务保护。

agent 的职责是根据项目上下文、用户选择、可用工具和最近的实际执行记录，准备本轮操作。输出应是可验证的工具计划或澄清请求。用户调整并执行计划后，由后台处理本地任务，结果呈现后结束本轮等待反馈。

## 1. 执行与恢复：小适配器加受控故障测试

### 怎么做

先写一个小型 ComfyUI 适配器，封装上传、提交、查询、监听、定向取消和获取产物。提交前持久化本地任务 ID、预先生成的 prompt_id、client_id、实际 API 请求、工作流版本、输入素材身份和资源边界。

任务应记录生成执行状态与资产保存状态，例如生成完成但保存待补；取消/失败后也可能有已保存的部分产物。UI 根据二者展示，避免一个简单的 success/failure 覆盖所有信息。

提交响应未知时进入“正在核实”，查询服务器队列和 history。只有能够确认没有执行的场景才允许按策略再次提交；ComfyUI 重启后证据缺失，维持未知/中断并向用户说明，不自动猜测成功或自动重新生成。

### 怎么测

大部分用可控的模拟 ComfyUI 服务或 HTTP/WS 代理测试：

- 接受请求后丢弃响应，确认应用不会重复提交。
- WS 断开，任务继续完成；重连后通过查询补齐状态。
- execution_success 已到但 history 稍后才出现。
- 重复事件和乱序通知不会增加重复素材。
- 保存第一个文件后第二个失败，重试仅补存缺失文件。
- 应用进程退出后恢复未结束任务。
- ComfyUI 重启导致任务查询失去证据。
- 取消请求与自然完成同时发生，最终以核实结果为准。

真实 ComfyUI 只验证关键路径：任务运行中关闭并恢复应用连接、定向取消本应用的测试任务、取消后收集现有产物。ComfyUI 重启测试安排在没有其他任务的专门时段，不作为日常调研的必要动作。

### 到什么程度就够

能明确每种情况的用户状态、是否允许重试、是否已有资产；未确认提交不能重复生成；反复补存不增加重复记录。形成状态转移表和恢复矩阵后即可支撑 spec。

## 2. 工作流工具：少量正常配置试跑

### 怎么做

每个工具形成一张契约：固定 API 模板与 hash、输入资产类型/数量、开放参数及范围、预设、输出角色、尺寸/帧数规则、资源限制、已实测情况。

现有测试继续作为基线，再补以下代表性运行：

| 试验 | 要解决的问题 |
| --- | --- |
| 单图编辑，在与输入匹配的正常尺寸下调亮 | 低分辨率测试的构图变化是否减轻；实际耗时/内存 |
| 单图编辑，明确的背景修改 | 已接入工作流对常用编辑诉求的适用范围 |
| Qwen 文生图快档/质量档各一次 | 快慢预设是否正确生效，正常耗时与资源差别 |
| 图生视频，正常配置、希望时长约 5 秒 | 默认视频任务耗时、内存、实际时长、输出可播放性 |
| 一个非正方形输入的放大/视频调用 | 输出比例、尺寸上限与输入拉伸处理 |

视频“5 秒”在现有工作流中对应约 5.167 秒的实际输出，应同时记录 requested_seconds 和 resolved_frame_count。输入比例默认跟随原图；需要改变比例时，在方案里明确裁切或拉伸的处理，支持方式受已准备模板约束。

所有试验使用副本、专属上传/输出目录、固定种子、批量 1、串行执行。耗时/内存超过本轮设定边界即定向取消并记录原因。保留原件，不为了试跑自动安装模型或改用户流程。

画面是否符合诉求由用户判断；调研记录可描述观察结果，不把一次满意或一次偏差当成模型能力保证。

### 到什么程度就够

每个首版入口都有一个真实可用的默认预设、参数契约、输出处理规则和粗略资源范围。不需要在 spec 前遍历所有尺寸、种子与模型组合。

## 3. 语言模型：先测计划，再测生成闭环

### 怎么做

默认建议采用可配置的在线语言模型服务。本机创作模型运行时内存已较紧，在线服务能减少本机资源竞争；这属于基于本机观察的设计建议，不是必须条件。已有本地服务也可以用同一计划协议验证。

先确认一个可用服务和配置方式。API 密钥只保存在后台配置/安全存储，不进入聊天记录、工作流或素材元数据。供应商和模型保持可替换。

计划至少包含：操作类型、工具 ID/版本、明确输入 asset_id、开放参数、项目上下文版本、本轮改动说明。遇到不明确引用或不支持能力时返回澄清/限制说明。

模型不能提供任意文件路径、节点代码、模型替换或新的连线。工具、素材、参数与预算由后台再次校验。用户点击执行时执行冻结的计划版本；用户改参数产生新的计划版本。

### 怎么测

准备约 20 条中文用例并写清期望操作，不执行 GPU：

- 明确的生成、编辑、放大、图生视频诉求。
- 使用项目风格但不重复说明。
- “选中的这张”“上一张”，以及多个候选时的歧义。
- 修改亮度而保留其他条件。
- 素材缺失、跨项目引用、项目切换。
- 请求不存在的工具或参数。
- 用户输入/素材备注中的无关指令不会获得文件操作权限。
- 正在创作时新增诉求返回当前状态，不假装启动第二轮。

检查 schema、真实输入引用、工具选择、重要设置变化、应否澄清。无效模型输出不进入执行；格式修复或模型重试有有限次数/费用边界，生成不自动重试。

计划测试后，再验证一个真实闭环：生成 → 用户选图 → 用户反馈 → 准备编辑方案 → 执行 → 新旧素材及来源关系可见。

### 到什么程度就够

至少一个服务能稳定完成明确用例，并对歧义/不支持能力作出正确处理。关键引用错误必须由后台阻断。形成 agent 输入/输出协议和用例记录后进入 spec。

## 4. 上下文引用：规则表和样例项目

### 怎么做

让后端维护明确的 context snapshot，而不是仅把所有历史对话交给模型猜：当前项目目标/风格、当前选择、用户指定的候选/最佳结果、最近已交付任务及输入、当前任务状态。

优先识别本轮明确的素材指代；“选中的”匹配当前选择，“刚才的”仅在唯一、清晰的本项目交付上下文中解析。最佳标记用于明确提及时的引用，不自动替换用户选中项。候选不唯一或指定项缺失时澄清，不找其他图代替。

计划准备后保存具体引用。项目切换、选中项变化或计划调整时，显示原计划所绑定的素材并明确更新操作，避免静默换输入。

### 怎么测

使用两个样例项目、多个候选、一个共享素材、一个移除项；依次模拟切换项目、改变选择、改变最佳、恢复旧版本、准备计划后改选。只检查准备出的方案与后台校验。

### 到什么程度就够

每种指代都有确定规则或明确澄清；执行记录能指向具体资产，不依赖容易重复的文件名。

## 5. 素材保存：小型存储原型

### 怎么做

建议区分物理内容文件、创作资产记录、项目引用、任务、输入/输出关系、候选批次。两个操作可产生不同资产记录而共享完全相同的物理文件，从而保留各自生成历史。

首版物理去重采用文件 SHA-256。像素相同但编码/元数据不同的 PNG 可记录内容关系，不默认合并原文件。末端预览与最终图通过输出角色关联，避免误显示成额外创作版本。

保存顺序：登记待保存产物 → 复制到应用同一磁盘的临时文件 → 校验完整性/媒体信息 → 完成文件落位 → 数据库事务记录已保存资产和来源。每一步记录可恢复状态；启动时核实未完成条目、缺失文件和未登记文件。

项目移除先软移除引用。永久清理单独执行，检查其他项目和保留来源关系；数据/文件同步失败有补偿日志，实际释放空间按最终删除的文件统计。

### 怎么测

用本次已有输出和少量测试文件，不用生成：重复导入、跨项目引用、移除并恢复、删除前引用检查、复制中断、文件落位后数据库提交失败、原结果丢失后补存、重启恢复。

磁盘不足可在存储适配器中注入写入失败，不真实填满用户磁盘。异常数据只写测试库/目录。

### 到什么程度就够

任一步失败不覆盖旧资产；补存不会再次生成；移除一处项目归属不损害其他项目；长期来源关系仍能解释。

## 6. 资源与其他任务：队列规则和预算检查

### 怎么做

应用后台是唯一的本产品提交入口。初始批量 1、串行执行，每次提交检查本地预算、工具参数与 ComfyUI 当前队列。

发现 ComfyUI 原界面或其他来源的任务时，默认等待它们完成并显示原因；只对本应用任务实施定向取消。检查存在时间窗口，最终串行顺序由 ComfyUI 保证，不宣称应用能独占 GPU。

不自动清空外部队列。释放模型缓存仅在服务器空闲、没有其他任务时按策略请求。显存/内存为瞬时观察值，不视作已为未来任务预留资源。

助手的一轮创作保持一个活动任务。期间新的创作诉求明确提示等待或取消；手动工具已受理的任务可按规则排队，这些队列规则在 spec 中写清。

本地资源限制与在线语言模型费用分别记录。提交前验证尺寸/实际帧数/批量，任务执行超时进入受控取消过程；LLM 的调用次数、输出 token 上限和估算费用有界。费用资料缺失显示未知，不能作确定价格承诺。

### 怎么测

模拟忙碌服务器、外部任务结束、预算已达上限、用户重复点击、LLM 请求超时。结合正常配置试跑确定初始预设与时间限制，暂不承诺准确剩余时间。

### 到什么程度就够

预算检查不可由模型绕过；排队顺序与忙碌提示清晰；取消和缓存操作不会针对其他来源任务。

## 建议的完成顺序与交付

1. 固定四类工具的参数契约与引用规则，形成可供模型使用的 schema。
2. 补少量正常配置试跑，确定初始默认值和实际限制。
3. 选用一个可配置模型服务，完成中文计划测试和一条真实反馈闭环。
4. 用小适配器/存储原型核实提交未知、断线补齐和保存补偿；重启/取消等高影响试验纳入专门验收阶段。
5. 写最终 spec：产品流程、agent 协议、工具契约、任务状态、资产模型、恢复矩阵、资源规则和验收用例。

交付应是少量有结论的材料：工具契约、预设试跑表、agent 用例结果、状态/恢复矩阵、资产关系和保存协议。未验证项明确标记，避免为了开始写 spec 而无限增加探索范围。
