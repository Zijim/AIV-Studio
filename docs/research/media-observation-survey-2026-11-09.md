# 媒体观察 tools 与生成视频检查调研

日期：2026-11-09（Asia/Shanghai）。

性质：讨论资料；核对本地源码、官方文档、作者项目及公开实现，未安装依赖、未下载模型、未上传素材、未运行付费模型或生成任务。以下推荐未经本项目视频样本实测，不表示已经具备这些能力，也不将 CREATIVE_AGENT_SPEC.md 中的 D05 标记为已确认。

## 1. 调研结论

1. 媒体观察 tool 是 Agent 可调用的能力接口；MCP 是对接工具的协议。观察工具可以直接调用本项目 Python 服务，也可以转接 HTTP 服务或 MCP server。
2. DeepSeek 官方 Responses 文档支持 function tools、函数调用结果里的图片；内置 mcp 工具类型被忽略。采用 MCP 时，需要本项目后端负责 MCP 客户端、工具映射和结果回传，不能只把 MCP 地址交给模型。
3. 现有公开实现包括专门的视频指标、训练过的视频评分模型、按目标组织证据的评估 Agent，以及候选视频比较和提示词改进循环。它们解决的问题各有范围。
4. 本项目正式应用目前没有生成视频内容的自动验收。已有媒体信息、首帧预览、图片输入基础；本地实验脚本能产出抽帧和音频，但没有自动完成质量判断。
5. 建议先实现本项目自己的受权限约束的媒体观察服务，通过原生 function tools 使用；保留视频模型和专用指标适配器。MCP 可作为后续接入方式，不作为首版前置条件。

DeepSeek 接口事实见 [官方 Responses 文档](https://api-docs.deepseek.com/guides/responses_api/)。MCP 的职责见 [官方架构说明](https://modelcontextprotocol.io/docs/learn/architecture)。

## 2. tool、MCP 和实际检查方法的关系

| 层次 | 作用 | 本项目中的可能形式 |
| --- | --- | --- |
| Agent tool 契约 | 模型可请求什么、传什么参数、收到什么结果 | inspect_media，指定素材、时间范围、检查问题及参考素材 |
| 调度与接入 | 执行调用、控制权限和资源、配对保存结果 | FastAPI 内部函数调度；必要时接 HTTP 或 MCP |
| 实际观察后端 | 解码、抽帧、检测、识别和分析 | PyAV / FFmpeg、视觉模型、VBench 指标、VideoScore2 等 |
| Agent 决策 | 结合用户目标和检查证据决定后续操作 | 补充观察、有限返工、交付，或说明关键项无法确认 |

MCP 自身不负责判断画面效果。一个 FFmpeg 包装服务可以提供解码和抽帧；一个视频理解服务可以提供视频问答；使用相同协议不代表具有相同能力。

DeepSeek 支持工具结果中的 input_image，因而可以先实现“工具抽取图像，主 Agent 观察”。接入 MCP 时，应用仍须把 MCP 工具描述映射为模型支持的 function，并把 MCP 返回内容转成模型支持的输入，同时处理鉴权、额度、错误和任务恢复。当前 API 的兼容性说明将内置 mcp 类型列为忽略项。[DeepSeek 官方说明](https://api-docs.deepseek.com/guides/responses_api/)

## 4. 公开项目如何实现

### 4.1 VBench：分维度的视频指标

VBench 为主体一致性、背景一致性、运动平滑度、运动幅度、美学和成像质量等维度提供专门评估方法。其自定义视频模式对部分维度开放，不应假设所有标准基准项目都能直接对任意成片执行。[官方仓库及自定义输入说明](https://github.com/Vchitect/VBench)

源码例子：

- 主体一致性：用 DINO 提取帧特征，比较当前帧与首帧、前一帧的余弦相似度，再汇总。
- 运动平滑度：通过插帧模型生成中间结果，与原视频相关帧进行差异比较。

见 [subject_consistency.py](https://github.com/Vchitect/VBench/blob/master/vbench/subject_consistency.py) 和 [motion_smoothness.py](https://github.com/Vchitect/VBench/blob/master/vbench/motion_smoothness.py)。

对本项目的判断：这些指标可以为特定维度提供信号；相似度和平滑度本身不证明指定动作发生。镜头运动、遮挡和剪辑也会影响信号，需结合目标解释。建议选择少量指标实测，不把整个基准评测栈作为首版必需依赖，也不直接规定通用通过分数。

### 4.2 VideoScore2：专门训练的视频评估模型

VideoScore2 接收视频和生成提示，分别评估视觉质量、文本符合程度、物理及常识一致性。它是专门训练的模型，有公开权重和单视频推理脚本。[作者仓库](https://github.com/TIGER-AI-Lab/VideoScore2)、[模型卡](https://huggingface.co/TIGER-Lab/VideoScore2)

核对其单视频推理源码：通过 qwen_vl_utils 准备视频输入，默认采样率为 2 FPS，模型放在 CUDA 上推理，再解析三个维度的分数。[vs2_inference.py](https://github.com/TIGER-AI-Lab/VideoScore2/blob/main/vs2_inference.py)

对本项目的判断：可作为独立评估适配器候选，优先比较它与 DeepSeek 抽帧方案对实际缺陷的识别差异。2 FPS 仍可能遗漏短暂问题；分数需要本地样本校准；部署显存、推理延迟和与 ComfyUI 的资源调度尚未实测。

### 4.3 VideoArgus：按每次任务制定标准，再调用工具取证

这是本轮与本项目设计最相关的公开实现之一。它先依据输入形成逐项标准，再为各标准执行证据计划，最后由视觉模型逐项评分并汇总；标准生成模型和评分模型可以替换。[作者项目说明](https://zzzmyyzeng.github.io/VideoArgus/)

实际工具包括：视觉问答、目标检测、局部裁剪、DINO 相似度、OCR、美学评分、深度、空间关系、闪烁信号，以及可选的外部参考图片搜索。[工具实现](https://github.com/zzzmyyzeng/VideoArgus/blob/main/videoargus/te_tools.py)

源码核对发现的边界：

- tool_vlm_qa 把采样帧作为图片发送给模型；最终 judge_criterion 最多附上 6 张生成视频帧，另可附 6 张源视频帧。
- sam_track 当前主要对采样帧逐帧执行 SAM 图像检测并汇总覆盖率；源码将完整视频传播列为可升级方向，不能把名称解释成已经完成稳定目标跟踪。
- 较密集的探针默认按 6 FPS 读取，最多 48 帧；实现从开头读取到上限，并非保证覆盖任意长度全片。
- flicker_probe 计算亮度和 RGB 均值变化等信号，不能单独证明或排除人物局部变形。

见 [te_tools.py](https://github.com/zzzmyyzeng/VideoArgus/blob/main/videoargus/te_tools.py) 与 [tool_executor.py](https://github.com/zzzmyyzeng/VideoArgus/blob/main/videoargus/tool_executor.py)。

对本项目的判断：最值得借鉴的是“检查项 → 证据计划 → 工具 → 逐项判断”的结构。工具集合、默认大模型、可选外部图片搜索及分数汇总规则应分别评估，不能整体照搬。尤其不引入自动外部参考搜索，也不扩大已确认的素材可见范围。工具出错或证据不足须单独表示，不能被转换为作品不合格后触发生成。

### 4.4 Evaluation-Agent：模型选择评估工具

Evaluation-Agent 根据评估问题选择维度和工具、准备测试提示、生成测试样本、运行评估，再根据结果继续或输出分析。其 VBench 路径的核心代码显式调用 sample 和 eval，并把指标结果回传给规划模型。[官方仓库](https://github.com/Vchitect/Evaluation-Agent)、[VBench 调度源码](https://github.com/Vchitect/Evaluation-Agent/blob/main/eval_agent/eval_agent_for_vbench.py)

对本项目的判断：它证明“LLM 不亲自完成所有视觉判断，而是调用专门评估工具”有公开实现。现有 VBench 路径主要评估生成模型能力，会组织新的测试样本；不能直接作为每个用户作品的轻量验收流程，否则引入额外生成、成本和任务范围。

### 4.5 VISTA：生成、比较候选、批评、改写提示

VISTA 是公开研究方案：组织有时间结构的创作计划，比较候选视频，分别收集视觉、音频和上下文反馈，再调整提示进入下一轮。[论文](https://arxiv.org/abs/2510.15831)、[方法与提示说明](https://arxiv.org/html/2510.15831v1)

对本项目的判断：可借鉴候选比较和按问题反馈的思路；论文中的效果不等于本项目已验证效果。本轮未核实到可直接接入本项目的完整部署工程。不能默认复制多候选、多轮生成预算。若后续因正常返工已有多个版本，可尝试对已有版本比较，不必专门增加生成次数。候选中最好的一份，也可能仍然不满足关键要求。

### 4.6 TwelveLabs：已有官方视频理解 MCP

TwelveLabs 提供官方 MCP 接入。当前文档区分 Jockey 跨视频集合推理服务与已迁移的单视频搜索、分析、嵌入工具；旧教程的地址和能力范围不能混用。[当前官方 MCP 文档](https://docs.twelvelabs.io/docs/advanced/model-context-protocol)

对本项目的判断：这是“能否接现成视频理解 MCP”的实际候选，但公开功能侧重内容理解、问答、定位和搜索，并不构成对生成缺陷验收可靠性的证明。对于单段新生成视频，优先评估单视频分析接口；不需要为了检查一个成片而开放项目全库的集合搜索。暂不接账号或上传任何项目素材。

### 4.7 基础组件与通用视频模型

FFmpeg 的 blackdetect、freezedetect、silencedetect 等可输出黑场、低变化画面和静音区间，用于发现需要解释的技术信号。它们不自行判断这些现象是否违背创作目标。[官方滤镜文档](https://ffmpeg.org/ffmpeg-filters.html)

支持视频输入的通用视觉模型也可承担定向问答。Gemini 文档说明其静态处理模式默认每秒抽一帧，快速动作可能丢失细节；Qwen3-VL 官方材料包含视频动态和时间戳相关能力。两者对本项目生成缺陷的识别表现仍需要样本验证。[Gemini 视频文档](https://ai.google.dev/gemini-api/docs/video-understanding)、[Qwen3-VL 官方仓库](https://github.com/QwenLM/Qwen3-VL)

FVD 这类生成模型评测指标，主要用于比较视频样本分布，不适合直接转换为单个作品是否达标的通用阈值。应区分模型基准评测、候选排序和单作品验收三种任务。[FVD 原始论文](https://arxiv.org/abs/1812.01717)

## 5. 对本项目的建议架构

以下为建议，未确认工具最终名称或具体参数。

~~~mermaid
flowchart TD
    A[DeepSeek 主 Agent] --> B[原生 function tool]
    B --> C[后台媒体观察服务：范围、预算、记录]
    C --> D[PyAV / FFmpeg：解码、抽帧、技术信号]
    C --> E[按需调用视频理解或专门评估模型]
    C -.可选接入.-> F[MCP 客户端与受约束的外部服务]
    D --> G[带来源和覆盖说明的证据]
    E --> G
    F --> G
    G --> A
~~~

### 5.1 Agent 看到的能力

先以 spec 已提出的 inspect_media 为入口，提供：

- 素材概览：技术信息、是否完整解码、时间轴概览帧。
- 定向观察：指定问题、时间区间和必要的已授权参考素材。
- 局部复查：更密集采样、局部裁剪，必要时调用视频观察后端。

这些操作可以是一个 tool 的不同模式，也可以后续按复杂程度拆分，暂不固定。

示意输入：

~~~json
{
  "asset_id": "asset_example",
  "focus": "确认人物拿杯后是否出现连续的喝水动作",
  "time_range": {"start": 1.0, "end": 3.0},
  "reference_asset_ids": ["reference_example"]
}
~~~

Agent 不需要提供文件路径、FFmpeg 命令或供应商地址。后台解析合法素材，再选择受配置和预算约束的处理方法。

### 5.2 返回什么

至少保存和返回：

- 原素材身份与原文件 hash，观察后端及版本，适用的任务目标版本。
- 实际观察范围：时间戳、采样密度、尺寸、裁剪位置；未覆盖部分和处理失败。
- 技术检查结果；逐项观察事实；证据帧或片段引用。
- 逐项状态：发现明确问题、已检查范围内未发现问题、无法判断。
- 资源使用记录；需要进一步观察时的具体问题。

通过图片观察时，返回真实图像内容并附身份和时间信息，不能只返回本地路径字符串期待远程模型自行打开。通过独立视频模型观察时，返回结构化结论和可核对证据；主 Agent 不因收到文字报告就自动认为所有判断可靠。

观察副本是原素材的派生证据，不自动成为项目关键素材。授权范围仍限用户指定素材、项目关键素材和本次创作成果；参考素材同样需要后台检查。MCP 集合、外部索引、缓存和摘要也不能绕过范围限制。

### 5.3 建议的执行顺序

1. 根据真实用户目标形成少量必要检查项；不把 Agent 添加的所有提示词修饰语变成硬要求。
2. 执行技术检查，并对整段视频做有明确覆盖范围的概览采样。
3. DeepSeek 根据概览和目标提出具体疑点。
4. 对关键疑点做局部复查；需要时交给视频模型或专用指标。
5. 仅在证据支持明确偏差时，进入有限自主返工；观察服务故障应重试观察或报告故障，不能据此重做视频。
6. 按既定交付原则处理：关键要求有足够依据且无明确未解决问题时直接交付；关键项仍无法判断时保留成果并说明。

普通审美意见不默认阻塞交付。返工后保留旧版；更高分或相对更好不自动代表满足全部关键要求。检查与生成应共用 Run 总资源约束，不能各自无限循环。

## 6. 接入顺序与实际约束

| 阶段 | 建议内容 | 目的 |
| --- | --- | --- |
| 第一阶段 | 本地解码、技术信息、带时间戳抽帧和裁剪；DeepSeek 图片观察；证据记录 | 建立可检查、可复查的基础，不先增加新的本地大模型依赖 |
| 第二阶段 | 为复杂动作接一个可替换的视频观察后端 | 与 DeepSeek 抽帧方案做实际对照，验证收益 |
| 第三阶段 | 按常见故障选择 VBench 指标、VideoScore2 或目标检测等 | 只补充真实有用的证据，控制运行复杂度 |
| 后续扩展 | 根据复用需求接 MCP adapter | 服务跨应用或远程工具，不改变素材权限和检查语义 |

已核对本机 GPU 为 RTX 4060 Ti、约 16 GiB 显存。ComfyUI 生成和本地评估模型需要协调显存；目前不建议把多个大型评估组件常驻作为首版默认。若选择本地观察后端，可评估串行加载和释放；具体可运行规模、量化效果和延迟待实测。

不预设固定采样率和通用通过分数。快速动作、慢动作、静止镜头、多镜头、口型等检查需求不同，采样和工具需要按目标选择。密集采样也只能增加证据，不能把未观察部分解释为已经验证。

## 7. 下一步验证建议

由用户明确指定少量视频及必要参考，覆盖成功、明显失败和难判断样本，不扫描项目素材库。人工标注具体问题及时间位置。

对照方案：

1. 技术检查 + DeepSeek 概览抽帧。
2. 在前者基础上加入按疑点局部加密观察。
3. 针对相同问题加入一个视频理解后端或 VideoScore2。

分别统计：

- 漏掉了哪些真实问题，误报了哪些正常创作。
- 动作符合程度、主体变化和短暂瑕疵各自的表现。
- 是否能给出正确的时间位置和可核查证据。
- 不确定结果是否如实保留，是否出现编造动作或错误自动返工。
