# 封存分析与评审意见

记录日期：2026-11-04  
对应规格：[v0.3 封存快照](SPEC_v0.3.md)  
状态：历史分析；评审问题尚未逐项收敛，不作为新版 agent 的实施要求。

## 1. 当时的现状判断

旧系统主要由后端组织“路由 → 专用生成 → 校验 → 确认 → 执行”流程。模型理解需求、选择已接入工具并设计正文与有限参数；后端准备上下文、控制步骤、执行提交和完成条件。

工具使用固定版本 API 工作流模板，运行时复制模板并按 bindings 写入参数、输入和归档信息。这个机制能隔离原模板与单次执行，但不等于模型可以自行决定查询哪些资料、读取工具结果并自由选择后续步骤。

旧系统没有生成结果驱动的自动评分、调参、再生成闭环。本次讨论也没有要求通过反复试生成寻找最优参数；用户关心创作耗时，希望在下一次正常生成前对参数作出合适判断。

## 2. 设计分析的变化

| 阶段 | 当时考虑 | 后续状态 |
| --- | --- | --- |
| v0.1 | 读取完整图并开放广泛节点参数，以变更协议修改执行图 | 已由后续设计替代，不作为当前推荐范围 |
| v0.2 | 稳定工具配置、明确开放常用参数；LoRA／模型组合以工具变体表达；任务调整不改全局默认 | 用户认可该方向；具体工具变体与更多开放项仍有待确定 |
| v0.3 | 共享语义判断原则，结合参数说明自主设计；不为所有工具和字段穷举触发表 | 用户认可并写入规格；未实现 |
| 本次封存 | 用户优先重新考虑 agent 架构，旧提案保留作未来参考 | 停止按旧规格继续细化或实施，不在本轮设计新架构 |

已认可的默认值约定是：普通调参只影响当前方案／任务；独立新任务从目标工具默认开始，续改根据明确来源配置起步；历史执行记录与最佳标记不会自动推广为工具默认。用户不需要逐个知道参数名，共享原则允许针对真实目标或反馈调整相关开放项，保留无关设置，依据不足时沿用基准。

本记录概括讨论脉络，归档的完整规格为 v0.3；不声称保存了 v0.1、v0.2 的完整原文或全部对话。

## 3. 最近一次评审的总体结论

稳定工具、有限参数权限、默认值隔离和共享判断原则具有可复用价值。主要问题集中在任务关系、意图与实际值的表达、决策职责和执行版本约定，不宜仅靠继续增加系统提示词解决。

下述建议只是当时评审意见。新版架构可能需要不同方案，应重新评估，尤其不应把旧的路由与编写阶段作为必然前提。

### R1. 任务关系与约束来源还不够明确

“新任务用默认、续改用来源”已经写清原则，但谁判定任务关系、如何确定唯一基准、素材用途与参数继承如何分开，还缺少足够明确的协议。

例子：生成一张竖版人物图后说“按这个风格，再做一个城堡场景”，可能是独立目标、原图修改或只用作风格参考。选中旧素材不等于应继承其画幅和预览配置。

当时建议记录任务关系、唯一参数基准、素材用途及来源证据。用户要求、助手推导和工具默认分别记录；用户明确要求的值即使恰好等于默认，也应保存约束，不能只根据参数差异推断用户意图。旧的 based_on 字段可作为起点，但不要混淆创作来源与参数基准。

### R2. 参数意图与最终执行数值需要分别保存

“自动跟随原图”和“用户固定指定尺寸”可能解析成相同数值。只存执行数值，会丢失续改时应该保留策略还是固定尺寸的信息。

当日对现有 Registry.normalize 做过纯函数离线核对，没有读写主数据库，也没有调用模型或 ComfyUI：

| 情况 | 得到的输出尺寸 |
| --- | --- |
| 640×960 输入，宽高留空自动处理 | 640×960 |
| 相同输入，明确填写 640×960 | 640×960，完整规范化参数与上一项相同 |
| 将上述规范化值用于 1280×720 输入 | 640×960 |
| 对 1280×720 输入重新使用自动处理 | 1280×720 |

该结果证明现有规范化记录无法单独区分两种意图；它不直接决定换输入时的产品行为。核对依据见 [registry.py](../../../backend/app/registry.py) 的编辑尺寸解析，代码链接指向现有仓库，可能在封存后变化。

当时建议保留自动策略／输入意图及本次解析值。执行值由后台从意图确定性产生，不让模型分别编辑两份互相独立的数据。进一步明确保持当前值、恢复工具默认、重新自动计算的区别。

### R3. 旧流程各模型阶段的决定权不明确

旧架构先路由选择工具，再加载专用资料；旧代码还会在编写前解析并冻结部分视频参数。v0.3 要求联合设计参数，但路由推导值、用户硬约束与专用规划建议的权限仍需要区分。

当时建议在旧流程内由路由负责需求、素材和真实约束，专用规划负责参数设计，后台负责合并、派生和校验。若读完资料才发现工具不合适，还需明确能否重选、如何计入修复额度以及失败如何结束。

这项建议高度依赖旧的固定阶段架构。新版 agent 应重新决定模型何时获取资料、选择或调用工具、依据返回结果继续，而不是自动采用上述阶段划分。

### R4. 参数有关联与开销值得接受是两个问题

提高生成面积或切换更慢的配置可能与质量诉求有关，但合法且有理由不等于用户愿意承受代价。资源上限主要回答可执行边界，不能完全表达可接受的创作耗时。

Qwen 从 4 步配置切到 50 步配置就是需要清楚说明的取舍；步数比不能直接视为耗时比。v0.3 有影响展示，但未完整定义用户没有明确取舍偏好时的成本选择。

当时倾向：缺少明确收益依据时保持当前或常规成本配置；显著增加开销的方案要对应具体目标并清楚展示，沿用整体确认，不增加逐参数审批。不要求为每个参数配置复杂阈值。此建议尚未单独讨论定案。

### R5. 工具变体粒度与首批范围可能写得过硬

固定模型组合分别提供是合理方向，但 v0.3 进一步要求 Qwen fast／quality 在新接口拆分，是否必须作为首批前置，仍值得讨论。

变体增加会影响路由、命名、指引和历史兼容。执行配置稳定，并不要求用户界面把所有变体作为互不关联的功能展示；后台可维护独立身份，界面按工具族组织并共享适用说明。

当时建议只为确实需要同时提供的组合增加新入口，并将旧接口兼容与新变体发布分开。这个评审不等于已决定恢复任意 LoRA／模型编辑权限，也不推翻此前稳定工具的共同方向。

### R6. 冻结和版本承诺需要具体执行方案

仅记录解析器版本号，不保证升级后仍能获得或执行旧解析逻辑。尺寸取整或自动处理规则改变后，重新解析旧方案可能得到不同配置；等待中间素材的两步任务也受影响。

当时提出需要在“保留多版解析实现”与“尽量提前计算并冻结配置”之间确定方案，较倾向后者：由后台保存冻结参数及图证据，执行时只解析声明的运行时绑定；真正依赖后续输入的部分通过契约约束。

不需要因此开放完整图编辑权限，但须区分可追溯、按冻结配置重提与像素级结果完全一致，不能仅凭保存 hash 承诺所有层面的复现。

### R7. 验收要覆盖模型判断，而不只有协议正确

固定模型响应、离线渲染与数据库检查能验证合并、权限和保存，却不能证明真实模型会根据请求合理选择参数。横版方案也可能符合 Schema，完整理由也可能缺乏实际依据。

当时建议增加小规模代表性模型行为评估：硬要求必须满足，诸如竖屏交付、锁定项、禁止字段；有多种合理方案的请求则检查关联、无关设置保持和取舍说明，不要求唯一参数组合。

这不需要向 ComfyUI 提交生成任务，也不是默认的成片评分或连续 GPU 调参循环。工程验证、模型行为评估和最终作品效果应分别表述。

## 4. 后续使用本记录

当时建议优先讨论 R1、R2、R3，因为它们直接影响继承与参数权威。现在架构前提已经调整，后续应先结合新版 agent 重新定位这些问题，再选用适用的设计。

规格第 15 节关于具体开放项、基础／Lightning 变体、偏好范围、预设和经验整理的未决问题仍保持未决。本次封存没有补选任何方案，也没有对新版架构作进一步调研或实现。
